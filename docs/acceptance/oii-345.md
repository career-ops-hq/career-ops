# OII-345 notification acceptance

The historical Node delivery path used `claimDelivery`, `releaseDelivery`, and
`completeDelivery` keyed by opportunity, channel, and report hash. Its stale
claim timeout and release-on-error could retry after a Discord timeout and
duplicate a delivered thread. The new Python LangGraph path keeps a business
delivery row (`queued → sending → delivered/uncertain`) authoritative over
checkpoints. `sending` or `uncertain` never retries automatically. The existing
Discord posting helper is only invoked after explicit notification enablement.

The isolated real input is the official Bosch SmartRecruiters posting
`https://jobs.smartrecruiters.com/BoschGroup/744000147797454-senior-software-developer-ai-agent-developer`,
opportunity `1`, scanned and scored with real JD and candidate inputs in a
temporary SQLite backup. Its independent score review approved the report;
range `2.75–4.75/5`, coverage `50%`, internal notification rank `3.75`, current
profile notification line `3.5`. Preview showed the range and coverage, with
no public scalar rank or shortlist tier.

With this real report and an isolated transport substitute, the first
delivery returned `delivered`; repeat delivery invoked the substitute zero
additional times. A copy with an explicit `employment=Fail` review gate and
another with a changed upstream JD both returned `ineligible`. The unit
recovery check verifies timeout and process interruption after claim cannot
reinvoke the sender. The CLI `send` command, without explicit enablement,
returned `Notifications disabled during migration acceptance`.

No Discord network call or external message was sent. This proves local
eligibility, formatting and at-most-once orchestration, not Discord service
availability. Both Career Ops schedules remain paused; live transport belongs
to the final OII-338 cutover and must not be exercised during migration
acceptance.
