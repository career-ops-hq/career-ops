# OII-337 acceptance progress

The apply agent runs in LangGraph. The existing Node Reactive Resume integration
is a callable tool: it duplicates or reuses a task-owned managed copy, patches
only that copy, exports a PDF, and never submits an application. The workflow
validates PDF readability and candidate identity, then binds the PDF, provider
metadata and six draft files to one version with file hashes. A successful
independent model review does not replace the user's final package review.

An isolated layout experiment reused the same real Bosch `resume.json` on a
separate task-owned Reactive Resume copy. Task PDFs now use 1.3 body and heading
line height, 4 mm section gap and 12 mm vertical margins; the base resume and
ordinary report path remain unchanged. The new export is two A4 pages. Both

it is not a final accepted PDF or user-confirmed package.
The Python renderer now rejects both kinds of non-source line-end hyphen before staging
an approved package, while allowing a genuine source hyphenated compound. Dedicated malformed-PDF regressions pass.
The provider schema exposes `/metadata/page/locale`, but changing the task copy
to `en-US` is not an evidenced fix: the real resume retains Chinese in the
candidate name and two employer names, and the PDF renderer enables its CJK
line-breaking path whenever it detects CJK content, independent of locale.
On 2026-09-25 the restarted local Reactive Resume service was reachable. Its
running image was Reactive Resume 5.2.8, built on 2026-08-25; the bundled CJK
hyphenation callback matched the checked-out source. A new export of the same
real Bosch resume remained two pages and still contained non-source line-end
hyphens. Restarting the service alone did not resolve the defect.
The stored `resume.json` uses ordinary spaces in phrases such as "full arc",
while the real exported PDF contains non-source `full-arc` and repeated line-end
hyphens. The provider's current font-registration callback returns Latin words
unbroken even when CJK content is present, so locale alone does not explain
the observed output. Inspecting the running `@react-pdf/textkit` code identified
the cause: it treats a following literal space as an ordinary word boundary,
but the provider callback returned a zero-width non-joiner plus space for that
same input. The resulting syllable was misclassified as a hyphenation point.
The provider callback now returns the original space and retains CJK character
breaking. Its focused 28 tests pass in the built image. After rebuilding and
recreating only the application container, the same real Bosch input exported
as a two-page A4 PDF at
`/private/tmp/oii337-restart-check.MKzEdS/resume-fixed.pdf`. `pdftotext -layout`
shows no non-source line-end hyphens; both pages were visually inspected with
no orphaned heading or obvious clipping. This is still a diagnostic export,
not the current LangGraph package or the user's acceptance.
