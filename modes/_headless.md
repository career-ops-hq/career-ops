# Headless and batch workers

AGENTS.md → "Headless / Batch Mode" sends you here. Read this file before spawning a headless worker, before a parallel fan-out of evaluators, and before writing or reviewing code that launches an agent CLI headless.

Headless worker command per CLI:

| CLI | Command |
|-----|---------|
| Antigravity CLI | `agy -p "prompt"` |
| Claude Code | `claude -p "prompt"` |
| Codex | `codex exec "prompt"` |
| Copilot CLI | `copilot -p "prompt"` |
| Gemini CLI | `gemini -p "prompt"` |
| Grok Build CLI | `grok -p "prompt"` |
| Hermes Agent | `hermes chat -q "prompt" --oneshot -Q --no-restore-cwd` (only explicitly non-writing workers; batch ranking does not support Hermes: see **Hermes workers** below) |
| Oh My Pi | `omp -p "prompt"` (no `evaluate`, `research`, `cover` or `pdf` worker: see **Oh My Pi workers** below) |
| **OpenCode** | `opencode run "prompt"` (falls back to `ollama launch opencode -y -- run "prompt"` if `opencode` binary is not in PATH) |
| Pi | `pi -p --no-approve --no-skills --skill .agents/skills/career-ops "/skill:career-ops <request>"` (Pi 0.79.1+; no `evaluate`, `research`, `cover` or `pdf` worker: see **Pi workers** below) |
| Qwen | `qwen -p "prompt"` |

**Pi workers.**
- **Headless:** `pi -p --no-approve --no-skills --skill .agents/skills/career-ops "/skill:career-ops <request>"` for one-shot workers, on Pi 0.79.1 or later; add `--mode json` when the caller parses events. Start the prompt with `/skill:career-ops`: Pi then puts the whole router in the prompt, while a plain prompt shows the model only the skill's name and description. `--no-skills` keeps a global skill named `career-ops` from taking the name. `--no-approve` runs the worker with the folder untrusted, even if you trusted it before, so the checkout's extensions and `.pi/` resources stay out; `--skill` still loads the router, and Pi 0.79.1 and later load `AGENTS.md` in an untrusted folder. Never give a worker `-a`: it trusts the checkout for the run and executes its project extensions without asking.
- **Workers:** Pi never asks before a tool call, and its default tools include bash, edit and write. The web runs the `evaluate`, `research`, `cover` and `pdf` workers without write tools (`pdf` without Bash too), so never run evaluations (`oferta`, `auto-pipeline`, batch), research, cover letters or CV PDFs headless under Pi (see `docs/SUPPORTED_CLIS.md`).
- **Example:** `pi -p --no-approve --no-skills --skill .agents/skills/career-ops "/skill:career-ops tracker"`

**Hermes workers.** Only explicitly non-writing workers may use `hermes chat -q "prompt" --oneshot -Q --no-restore-cwd`, and only when that run's Hermes configuration enables no tool that can run commands or code or change files (in Hermes 0.23.4 that includes the `terminal`, `file` and `code_execution` toolsets). The web's audited grant denies Bash and every write tool to every non-writing kind (`WRITE_CAPABLE_TOOLS` in `web/src/lib/claude-invocation.mjs`), `pdf` included, but the web does not enforce that deny list on Hermes. It permits non-writing Hermes workers, and they inherit Hermes's configured tools, approvals, memory and project-context rules, which career-ops can neither set nor check. Non-writing status alone therefore does not keep a Hermes worker within the rule below. That configuration also rules out a standalone evaluation (`oferta`, `auto-pipeline`, batch): run by hand, it must write its report and tracker row itself, while the web's `evaluate` worker hands those writes to the backend. The web refuses Hermes for any worker whose capability record has `writes: true` (`isCliAllowedForCapabilities` in `web/src/lib/cli-fencing.mjs`) and runs the other kinds with a notice that Hermes cannot be permission-restricted. Batch ranking does not support Hermes: `rank-pipeline.mjs --cli hermes` exits with an error. See `docs/HERMES.md`.

**Oh My Pi workers.** No career-ops fence covers `omp -p`, and the web runs Oh My Pi with a notice that it cannot be permission-restricted. Its core tools include `bash`, `edit` and `write`, and opening the checkout loads the project's settings, extensions, hooks and tool modules with no trust step. `--no-tools --tools read,grep,glob` confines a run to those built-in tools and loads no extensions, hooks, custom tools or MCP servers (Oh My Pi CLI reference, v19.2.1), which matches the write side of the web's grant for the read-only kinds. Run by hand, though, those workers need what the web withholds: an evaluation writes its report and tracker row, and a CV PDF needs Bash for `node generate-pdf.mjs`. So, as with Pi, never run evaluations (`oferta`, `auto-pipeline`, batch), research, cover letters or CV PDFs headless under Oh My Pi; run them from the web UI with Claude Code or in an interactive `omp` session you are watching. Batch ranking already calls `omp --no-tools -p` and needs no tools.

**Headless worker permissions — one rule for every entry point (#2876).** A worker never gets more write power headless than the web grants the same worker kind. The web's grant is the audited one: `WRITE_CAPABLE_TOOLS` and the per-kind deny lists in `web/src/lib/claude-invocation.mjs` (`pdf` has had no Bash since #2172 and must never regain it).
- Never add a blanket auto-approve flag (`--dangerously-skip-permissions`, `--always-approve`, `--yolo`, `--full-auto`, …) to a new spawner. If a CLI has no per-tool deny list to express the restriction, withhold the write-capable workers from that CLI instead of auto-approving them.
- Prefer moving the write out of the agent: the worker returns content and the harness writes the file or renders the PDF, which is how the web's `pdf` path stays read-only.
- `batch-tailor.mjs` and `batch/batch-runner.sh` still pass such a flag. That is known debt tracked in #2876, not a precedent. `tests/headless-permission-flags.test.mjs` discovers every code file that passes one and fails on any file outside that list, or on any grant added inside it. It sees flags only: a CLI that auto-approves headless without one is outside what it can check (`batch/batch-runner.sh` also launches `opencode`, `gemini` and `qwen` with no flag), so review such a launch against this rule by hand.

**Parallel fan-outs — reserve report numbers first.** Before spawning N parallel evaluators, reserve the range: `node reserve-report-num.mjs --count N` (prints e.g. `042-049`); hand each worker its own number. The allocator treats report files, sentinels, tracker row IDs, tracker report links, and tracker numbers still named in `status-log.tsv`, `data/follow-ups.md`, `data/salary-observations.tsv` or `data/contacts.tsv` as occupied, so a deleted or merged-away row's number is never handed to a new application; each slot claim is individually atomic (on collision, claimed slots are released and the reservation restarts past it — permanent, harmless gaps). Release with `node reserve-report-num.mjs --release 042-049` when done; stale sentinels are GC'd after 4h, so reserve right before spawning. Never let parallel workers compute `max+1` themselves — that is the #749 race.
